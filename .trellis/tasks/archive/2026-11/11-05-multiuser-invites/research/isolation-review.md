# Multi-user isolation: critical review

Research only, 2026-11-05. Product scope and administrator/invite policy remain pending. The proposed identity/session/invite database plus private ledger databases is defensible: the schema inventory is 48 business tables plus `users` and `sessions`, while current route groups and nested services capture one ledger handle. It avoids relying on hundreds of individually correct owner predicates. It does **not** isolate external worker jobs, filesystem paths, or process-lifetime state automatically.

## Findings that must shape the design

1. **External cutout jobs bypass ledger isolation.** `packages/server/src/routes/item-cutouts.ts` forwards job status, cancellation, preview and image requests to a shared worker using only the supplied opaque `jobId`. There is no persisted account ownership check. Record job ownership durably and verify it before contacting the worker for every operation; random identifiers are not authorization. Define cleanup if worker creation succeeds but ownership persistence fails. Cover restart as well as two concurrent users.

2. **Backups still select the original owner's file.** `services/portability-service.ts:1204` derives `join(dataDir, 'jizhang.db')` instead of using its selected `Db`; backup listing also uses `dataDir/backups`. Assistant nested portability services receive `config.dataDir` (`services/assistant-orchestrator.ts:103`, `routes/assistant.ts:454`). Carry an explicit tenant storage descriptor (`db`, `dbFile`, `dataDir`) through every constructor, including indirect tools. Never allow a member request to select root storage. Check raw owner backups for legacy `users`/`sessions` and saved AI credentials before treating them as ordinary user exports.

3. **Assistant state has a lifecycle, not just a database dependency.** `routes/assistant.ts:228-295` constructs conversation locks, confirmation promises, generation runners, subscriber services and batch runners, calls both recovery routines, then registers shutdown hooks. `assistant-generation-service.ts:460,470,1110` keeps subscriber/terminal/canceller maps; `assistant-generation-runner.ts:215` keeps active work. A request-scoped reconstruction would repeatedly mark current work interrupted and lose cancellation/subscription handles. Construct exactly one immutable service context per open tenant; bind it before any asynchronous work. Never use a mutable process-wide current user/database. Recovery must run once on each newly opened tenant context, and shutdown/eviction must drain runners and streams before closing its DB. `index.ts` currently closes only the one original DB.

4. **Existing SSE checks prove conversation ownership, not account ownership.** Replay and cancellation currently check generation-to-conversation membership (`routes/assistant.ts:354-378`); subscription maps are keyed by generation ID. Select the account context before these checks and before writing the SSE response head. An already-open stream must remain bound to its original account even after another request logs in. Current request-time auth does not imply immediate revocation of an established stream; explicitly choose expiry/logout/account-disable behavior if that capability enters scope.

5. **Authentication changes must not inherit single-user assumptions.** `routes/auth.ts` permits only `config.username` and derives `/auth/me` from configuration. `services/auth-service.ts:120` deletes **all** sessions when CLI `setPassword` runs; ordinary password change is already scoped at line 217. Centralizing the tables without removing these assumptions either prevents invited users from logging in or signs out unrelated users. All protected route groups must remain inside the auth plugin's encapsulation context, as required by the directory spec. Obtain the tenant mapping only from a validated central session and immutable server-side account ID; missing/failed mapping must fail closed, never fall back to the owner ledger.

## Registration and migration failure semantics

- The app enables WAL (`db/index.ts:22`). A transaction spanning attached SQLite files is not crash-atomic in WAL mode: each file commits atomically, but a host crash can leave only some files updated. [SQLite's ATTACH documentation](https://www.sqlite.org/lang_attach.html). Do not claim an `ATTACH` transaction makes invitation consumption plus ledger creation all-or-nothing.
- One viable sequence is to initialize a fresh, private provisional ledger under a server-generated immutable account ID, then atomically create/activate the identity, persist its mapping and consume the invitation in **one central database transaction**. Alternatively use a durable provisioning state/reservation with idempotent restart recovery. Neither sequence is finalized here. In either case, interruption before/after each durable step must have a documented recovery outcome; no active account can point at an uninitialized ledger. Concurrent redemptions require a guarded update/unique constraint and exactly one successful consumption. Duplicate username or failed initialization must not silently burn an invitation without a recovery path. Orphan cleanup must check committed mappings before removing any directory.
- Seed new ledgers from schema/default seed data; never clone the owner's populated DB. Paths must derive from server-generated IDs under the intended storage root, not usernames or client-supplied paths. Keep credential/invitation tokens out of ledger exports and ordinary logs. Registration is public only by explicit route exception; preserve mutation CSRF defenses and bounded request/password handling.
- Initial-owner migration must identify the existing account explicitly and preserve its ledger data and stable identity. Persist that ownership decision once; changing `JIZHANG_USERNAME` later must not reassign `jizhang.db`. Empty/ambiguous legacy identity state needs a deterministic bootstrap/repair path. The first public registration must never acquire existing data or owner privileges by winning a race.
- Copying legacy identities into a central DB and recording original-ledger ownership is itself a multi-file migration. Use an idempotent migration marker and verify completed state before serving requests. Choose explicitly whether existing sessions are preserved or invalidated. Leaving legacy auth tables for additive compatibility requires defining their authoritative/inert status and avoiding credentials leaking through member backup features.

## Backup and rollback constraints

The database spec requires additive migrations and readable old files, but that does not guarantee that an old single-user binary can operate a new multi-file deployment. After registration, it cannot see new users/ledgers; it may also reactivate stale legacy sessions or overwrite the original identity through the existing CLI. Resolve this compatibility gap in the implementation plan/spec rather than describing rollback as automatic.

`cli-db.ts` still backs up/restores one configured database. Separate user-data export from full-system recovery. A full recovery needs central identity/mapping state and all referenced ledgers, a manifest/version, and a consistent maintenance boundary. Keep restore offline. Specify which files a rollback restores together, how newer registrations/data are preserved or intentionally excluded, and how unsafe mixed-version startup is prevented. A pre-migration `VACUUM INTO` snapshot of only `jizhang.db` is not a backup of the resulting multi-user system.

## Minimum high-value verification

- Two accounts exercise cross-account IDs across reads, mutations, references, import batches, assistant replay/snapshot/cancel/confirm, cutout image/status/cancel and backup/export. Responses reveal no foreign data and cause no foreign mutation; seeded identical IDs remain independent.
- Delay A's provider work, run B's requests, then complete/cancel/reconnect A: persisted events, tool writes, locks, credentials and stream delivery remain in A's context. Restart unfinished generations/batches and verify recovery once per tenant; closing one context does not terminate another's work.
- Concurrent invitation redemption, duplicate usernames, failure injection at each provisioning/migration step, and restart retries. No invitation double use, active account with missing storage, owner fallback, or unintended orphan deletion.
- Original owner bill/config/conversation counts and representative contents remain unchanged after migration; invited ledgers contain defaults only. Password rotation for A preserves B's session. Test CLI backup/restore against the explicitly chosen multi-file contract.

No source changes or operational migration were performed during this review.
